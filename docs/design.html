第1章システム構成

1.1構成方針

本システムは ビルド工程を持たない素の HTML / CSS / JavaScript で実装し、 GitHub Pages でホスティングする静的サイト構成を採用する。サーバサイドを持たないため、 運用コストが極小で、少人数・非常駐の運営体制 (対応2〜3名) に適合する。

  • データ層はブラウザ内 localStorage をデモ用永続化ストアとし、すべて SkyRentStore / SkyRentAPI の抽象化層を経由してアクセスする。
  • 本番運用時は、この抽象化層の実装のみを GAS / AWS 等の REST バックエンド に差し替えることで、画面側のコードを変更せず移行できる (5.4節)。
  • 決済 (Stripe 等) ・メール実送信は 拡張ポイントとしてインタフェースを確保 しつつ、初期リリースでは現地決済・通知ログで代替する。

第2章画面遷移図

2.1公開サイト (予約フロー)

トップページから検索・詳細を経て予約フローに入る。予約フローは 1画面 (booking.html) 内で「情報入力 → 確認 → 完了」の3ステップを状態遷移 させる構成。 現行の2カテゴリ (一般レンタカー・キッチンカー) はいずれも車両カテゴリのため、免許証情報入力欄と確認ステップを表示する (将来 物品カテゴリを追加した場合は動的に非表示化される)。

2.2管理画面 (ダッシュボード中心)

ログイン後は dashboard を起点に、共通トップバーのメニューから各管理画面へ遷移する (ハブ&スポーク)。 全拠点 (北見・釧路) を一画面で横断把握できる構成。

4.3SkyRentPricing.calculate 料金決定ロジック

署名: calculate({asset, start, end, quantity, options:[optionObj], coupon:{amount}|null, seasons?}) → {lines:[{label, amount}], days, hours, plan, subtotal, discount, total}。 利用期間から最適な料金プランを自動選択し、加算・割引を順に積む。

  • プラン選択は上から順に評価し、最初に条件を満たしたプランを採用 (月割 → 週割 → 時間貸 → 日貸)。週割・月割は端数を日割りしつつ、次の週/月料金を超えない上限で丸める。
  • ハイシーズンは sky-rent.high-season を自動参照し、利用期間と重なる日数分だけ基本料金に rate% を加算。
  • 拡張性：長期割引・会員ランク別料金などは、加算ルールを 1 関数追加するだけで組み込める設計 (要件7章「料金計算モジュールの拡張性」準拠)。

第5章拡張設計

5.1新カテゴリ追加手順 (エンジニア不要)

要件定義書で最重要とされる「新カテゴリ追加はエンジニア不要で管理画面のみ」を、EAV (customFieldDefs) と統合 assets モデルで実現している。 コード変更・再デプロイは一切不要。例えば将来「冷凍車」のようなカテゴリを増やす場合も、以下の手順のみで公開まで完結する。

  1. カテゴリ作成 — categories.html で新カテゴリを追加 (name / type=vehicle|item / icon / sort)。
  2. カスタム項目定義 — 同画面のカスタム項目エディタで customFieldDefs を設定 (key・ラベル・型・単位・選択肢・filterable)。これが登録フォーム・詳細スペック表示・検索フィルタに自動反映される。
  3. アセット登録 — vehicles.html で車両を登録。カスタム項目の入力欄が定義に応じて自動生成され、値は customFields に格納。料金プラン・在庫・(車両は)車検期限を設定。
  4. オプション紐付け — options.html で専用オプションを作成し categoryIds に新カテゴリを指定 (共通オプションは自動適用)。
  5. 公開サイトの検索・詳細・予約フローに即時反映。フロントの改修は発生しない。
設計の要：画面側はカテゴリの customFieldDefs を読んで UI を動的生成するため、項目の増減がデータ変更だけで完結する。filterable:true の number 項目は「以上」、select/text は完全一致で検索に効く。

5.2決済手段の追加 (payment.method)

初期リリースは現地決済 + 請求書払い。オンライン事前決済 (Stripe 等) は対象外だが、拡張できる設計を確保済み。

  • reservations.payment.method は文字列 enum。既に 'online' のラベルを PAYMENT_LABELS に定義済 (「オンライン決済」)。
  • 追加手順: ① booking.html の決済選択に online を追加 → ② 予約作成前に Stripe Checkout / PaymentIntent を発火 → ③ 成功コールバックで createReservation({paymentMethod:'online', ...}) を実行し payment.status='paid' を設定。
  • 請求書払いと同様、会員フラグや拠点で選択肢の出し分けが可能な構造。金額は SkyRentPricing の total をそのまま Stripe 金額に用いる。

5.3メール送信の実装差替 (notify)

予約確認・状態変更・クーポン発行・請求書発行などの通知は、すべて SkyRentStore.notify(type, message, refId) の一点に集約されている (デモではログ化)。

  • 本番はこの関数内から実送信を呼ぶだけでよい: GAS の MailApp.sendEmail / SendGrid・Amazon SES 等の REST API。
  • 宛先は refId から予約・会員を引き当てて解決。呼び出し側 (各画面) の変更は不要で、送信基盤を一箇所で差し替えられる。
  • 通知種別 (type): reservation / status / member / coupon / invoice。テンプレートを type ごとに用意すれば HTML メール化も容易。

5.4本番移行 (localStorage → REST API)

js/config.js の GAS_URL を実 URL に設定すると、SkyRentAPI が fetch ベース実装へ切り替わる (isConfigured 判定)。 画面側は SkyRentAPI しか呼ばないため、以下のエンドポイントを用意すれば移行が完了する。

SkyRentStore 相当HTTP メソッド / エンドポイント (例)備考
list / assets / categories / locationsGET /assets, /categories, /locationsマスタ参照。クエリで絞込。
searchAvailableGET /search?categoryId&start&end&filtersサーバ側で空き算出。
availabilityGET /availability/{assetId}?start&end在庫・重複判定。
createReservationPOST /reservationsトランザクションで空き検証+採番。
updateReservationPATCH /reservations/{id}状態遷移・ポイント副作用はサーバ側で。
registerMember / loginMemberPOST /members / POST /auth/loginパスワードハッシュ化・トークン発行。
createInvoice / setInvoiceStatusPOST /invoices / PATCH /invoices/{id}請求・入金管理。
getDashboard / getRevenueGET /dashboard / /revenue集計はサーバ側で最適化可。

エンティティ = テーブル (categories / locations / assets / options / members / reservations / invoices) に 1:1 でマッピング。coupons・pointHistory・customFields は JSON カラム or 子テーブルのいずれでも可。

第6章非機能設計

6.1レスポンシブ設計

  • スマホ最優先 (要件)。公開サイトは style.css + public.css で流動レイアウト。検索・詳細・予約フローをタッチ操作前提で設計。
  • 管理画面は manage.css で共通トップバーをハンバーガーメニューに集約。少人数・非常駐運営が外出先スマホから全拠点 (北見・釧路) を管理できる。
  • 幅の広いテーブル (予約一覧・ガント) は .card 内で横スクロールさせ、レイアウト崩れを防止。

6.2セキュリティ (XSS対策・認証)

  • XSS対策：ユーザー入力・データ由来の文字列は必ず esc() で HTML エスケープしてから DOM 挿入する (開発コントラクト規約)。& < > " ' を実体参照へ変換。
  • 認証 (デモ)：会員は email + password (平文) で sessionStorage セッション管理。本番はパスワードのハッシュ化 (bcrypt 等) とサーバ側セッション/JWT が必須 (5.4節で移行)。
  • 権限：請求書払いは invoiceAllowed フラグ、ポイント手動操作・帳票発行は管理画面 (従業員権限) に限定。従業員管理で拠点・権限を設定。

6.3データバックアップ / 復元

  • profile.html から全 sky-rent.* データを JSON でエクスポート / インポート可能。localStorage 運用時の消失・端末移行に備える。
  • シード投入は DATA_VERSION で管理。バージョン不一致時のみ再投入し、settings.* (ポイント設定・振込先) は温存する非破壊マイグレーション。
  • 本番移行後はバックエンド側の RDB バックアップに一本化する。

6.4多言語 (i18n) ・可用性・性能

  • 多言語：公開サイトは SkyRentI18n で日英対応 (data-i18n 属性 / t())。将来の中韓は辞書追加で拡張。資産名は日本語を基本に nameEn を併用。
  • 可用性：静的サイト + GitHub Pages (CDN 配信) によりサーバ障害点が少なく、常時稼働に強い。
  • 性能：ビルド不要・依存 CDN なしの軽量構成。データは localStorage で即応。集計 (ダッシュボード・売上) はクライアント側で完結し、本番移行時はサーバ集計に置換して更にスケールさせる。
  • 通知：非常駐前提のため、予約・状態変更をメール自動通知 (notify) で担保する運用設計。
